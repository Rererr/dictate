## 1. 範囲

最小試作に含めるものは次の七つである。

- グローバルホットキー（押している間だけ録る）
- Apple SpeechTranscriber のライブ認識（`.volatileResults` + `.fastResults`、キーを離したら finalize）
- 読み辞書の決定的置換
- 末尾コマンド「送信して」と「改行して」
- 前面アプリへの挿入（AX、失敗時はクリップボード退避 + ⌘V + 復元）
- 任意の LLM 整形（Qwen3-8B、フィラーと句読点のみ、数値マスク、予算 1 秒）
- 浮遊パネル（部分結果と状態の表示）と履歴

次のものは作らない。

| 作らないもの | 理由 |
|---|---|
| 2 トラック録音、融合、要約 | 議事録側の所有（handoff §1） |
| 編集モード（選択文の置換） | LLM の指示追従が前提で、8B は編集指示を無視する（handoff §2.3） |
| 宛先アプリや直前の文に合わせた文体調整 | LLM の役割をフィラーと句読点に絞ったため、渡す先がない |
| 二度押しのハンズフリー | 録音の開始と終了を本人が握る形だけで試作の問いに答えられる |
| 設定画面 | 設定は JSON ファイル 1 枚で足りる（ADR-9）。ホットキーだけは登録の窓を持つ（ADR-4） |
| 音声の保存 | 後処理は生テキストから再計算でき、音声を残す用途がない（ADR-7） |
| ログイン時の自動起動 | 試作の間は手で起動する。launchd は入れない |

## 3. 構成

### 3.1 リポジトリの配置

```
dictate/
  Packages/SpeechCore/        共通核。独立した Swift パッケージ
    Package.swift
    Sources/SpeechCore/
    Tests/SpeechCoreTests/
  Package.swift               アプリのパッケージ。SpeechCore をパス依存で取る
  Sources/DictateKit/         後処理と履歴。AppKit に依存しない
  Sources/Dictate/            常駐アプリ本体（AppKit）
  Tests/DictateKitTests/
  scripts/bundle.sh           build/Dictate.app を組み、署名する
  scripts/test.sh             核とアプリのテストを両方回す
  eval/                       20 文の評価シートと採点スクリプト
  docs/design.md
```

アプリ側を `DictateKit` と `Dictate` に分けるのは、後処理（コマンド判定、数値マスク、整形の検証、履歴）を画面も権限もなしにテストするためである。
`Dictate` に残るのは、権限と OS のイベントに触れる部分（ホットキー、パネル、挿入）だけになる。

### 3.2 共通核 SpeechCore の境界

SpeechCore が持つのは handoff §1 の三つ（音声の取り込み、ライブ認識、読み辞書）である。
議事録側は `.package(path: "../dictate/Packages/SpeechCore")` で取り込む。

| 型 | 役割 | 公開する面 |
|---|---|---|
| `AudioChunk` | 音声バッファの受け渡し単位。`AVAudioPCMBuffer` を包む | `init(_ buffer:)`、`buffer` |
| `MicrophoneCapture` | AVAudioEngine でマイクを取り、機器の形式のまま流す | `start() -> AsyncStream<AudioChunk>`、`stop()` |
| `LiveTranscriber` | SpeechAnalyzer と SpeechTranscriber を包む。入力は任意の形式で受け、認識器の形式への変換は内部で行う | `start(input:) -> AsyncThrowingStream<TranscriptEvent, Error>` |
| `TranscriptEvent` | 認識結果 | `.volatile(String)`、`.final(FinalSegment)` |
| `FinalSegment` | 確定結果 | `runs: [Run]`。`Run` は `text`、`confidence: Double?`、`timeRange: ClosedRange<TimeInterval>?` |
| `TranscriptAccumulator` | 届いたイベントを「いまの全文」に畳む | `apply(_:)`、`text`、`finalText`、`runs` |
| `YomiDictionary` | 読み辞書の置換 | `init(entries:)`、`init(tsv:)`、`apply(_:) -> Replaced`（置換後の文字列と置換箇所） |

実装で、承認時の表から二点を変えた。
一つ目は `finish()` を無くしたことである。
入力のストリームが終わると `LiveTranscriber` が確定まで進み、結果のストリームも終わる。
`finish()` を別に持つと、認識器の開始が終わる前に呼ばれた場合の扱いを利用側が毎回書くことになる。
キーを短く押して離すと実際にこの順になる。
二つ目は、バッファを `AudioChunk` に包んだことである。
`AVAudioPCMBuffer` は Sendable でなく、`AsyncStream<AVAudioPCMBuffer>` のままでは、アクターをまたいで渡す利用側が Swift 6 の並行性検査を通せなかった。
流した後のバッファを書き換えないという約束を、核の型 1 か所に閉じ込める。

`.final` は 1 回の発話で複数届きうる（認識器が区間ごとに確定する）。
利用側は確定済みの区間を順に連結し、その後ろに最新の `.volatile` を付けたものを「いまの全文」として扱う。

`LiveTranscriber` の入力は `AsyncStream<AudioChunk>` で、音源を知らない。
形式の変換を `LiveTranscriber` が持つので、議事録側がプロセスタップの音声（48kHz 2ch）でライブ字幕を出すときは、タップのバッファを `AudioChunk` に包んで流せば足りる。
合成音声を 48kHz 2ch に変換したファイルで、16kHz mono と同じ確定テキストが得られることを確かめた。
2 トラックの字幕は `LiveTranscriber` を 2 本同時に動かすことになる。
同時に動くかは未確認で、確かめるのは議事録側が取り込むときになる。
音源を抽象化するプロトコルは置かない。
利用者がマイクしかない現時点では実装が一つで、プロトコルが表す差分がまだ無いからである。

核に入れないものも決めておく。
ホットキー、挿入、パネル、LLM、履歴、コマンド判定は音声入力の都合であり、`Dictate` と `DictateKit` に置く。
プロセスタップ録音（`systap-record.swift`）の取り込みは handoff §5 に挙がっているが、今回は入れない。
使うのが議事録側だけで、こちらでは動作を確かめる経路が無いからである。

この範囲は、議事録側の設計（`~/personal-dev/meeting-minutes/docs/design.md`）の前提と食い違っている。
議事録側は、一括認識の CLI とタップ録音の CLI を「`dictate` の核ができた時点で核に置き換える複製」とし、出力機器の変更時にタップを作り直す処理と、マイクとタップの同一機器セットでの同期録音も、直す場所を `dictate` の核としている。
今回の SpeechCore に入るのはライブ認識だけで、一括認識もタップ録音も入らない。
このまま両方が進むと、二つのタブが同じ機能を互いに相手へ預けた状態になる。
一括認識は handoff §1 が核として挙げた三つに入っておらず、タップ録音は handoff §5 にだけ「核に取り込む」とある。
どちらを核に入れるかは本人の判断として §10 の 6 に置く。

認識モデル（ja-JP のアセット）が未導入の場合、SpeechCore はエラーを返すだけで、取得の要求はしない（handoff §6 のダウンロード規則）。
導入済みかは `SpeechTranscriber.installedLocales` で見る。
`AssetInventory.status(forModules:)` は、導入済みで認識できる状態でも「導入済み」ではなく「対応」を返したので使わない（実装中に実測）。

### 3.3 読み辞書の置換方式

辞書は「表記」と、任意の「読み」の組である。
置換は、認識結果を単語に分け（CFStringTokenizer、`yomi.swift` と同じ読み取得）、連続する単語の読みを連結したものが辞書の照合キーと一致した区間を、表記に置き換える。
一致は単語境界に限り、長い区間を優先する。

照合キーは、人が知っている読みではなく、同じ読み取得の関数が返す文字列である。
この関数の読みは実際の読みと一致しないことがある。
実測では「嚥下」が「えんか」、「発赤」が「はっせき」、「良眠」が「りょうねむり」になり、長音は母音に展開される（「サーバー」が「さあばあ」）。
人が「えんげ」と書いた辞書は、認識結果の側が「えんか」と読まれるので一致しない。
そこで、照合キーは読み込み時に表記を同じ関数にかけて作る。
読みを明示した行（英字の語など、表記からは読みが出ないもの）も、同じ関数を通して正規化する。

単語境界に限るのは、読みの部分一致で別の語を壊さないためである。
たとえば「けいかん」を単純な部分文字列で引くと、「けいかんえいよう」の途中にも「たいけいかんり」の途中にも当たる。

読みで引く方式には、同じ読みの別の語も置き換えるという限界がある。
付録 B の辞書で実測すると、「演歌を歌った」が「嚥下を歌った」に、「何円か払う」が「何嚥下払う」になった。
後者は「円」と「か」という別々の語の読みを連結して当たっており、単語境界に限るだけでは防げない。
短い読みの語ほど当たりやすい。
この限界は設計では埋めず、辞書に入れる語を選ぶ側で避ける。
誤って当たる量は語によって大きく違う。
金額と介護の話題に寄せた 43 文で試すと、誤置換 16 件のうち 13 件が「嚥下」で、その大半は金額の「円か」だった（「千円か二千円」）。
経管栄養、褥瘡、発赤、良眠では、同じ読みになる語の組み合わせを作れなかった。
手元の技術文書（日本語 43 万文字）では、付録 B の全語で誤置換は 0 件だった。
そこで「嚥下」は辞書の初期値から外した。

空白は読みが空なので、一致する区間の端には含めない。
含めると、表記が正しくても隣の空白ごと置き換わり（「褥瘡 なし」が「褥瘡なし」）、空白だけの差が置換として数えられる。
Apple は数字の前に半角の空白を入れるので、この扱いが無いと §7.2 の誤置換の件数が汚れる。
§7.2 の「誤置換 0 件」は台本 20 文にしか当たらないので、この種の誤りは評価では見つからない。

直せるのは読みが正しく出た誤りに限る（「軽管栄養」は直り、「経過栄養」は直らない）。
この限界は handoff の元文書（`06` §6）のとおりで、設計では埋めない。

辞書ファイルは TSV（`表記<TAB>読み`、読みは省略可）で、`~/Library/Application Support/Dictate/dictionary.tsv` に置く。
起動時に読み、メニューの「設定と辞書を再読み込み」で読み直す。

### 3.4 処理の流れ

状態は五つで、一方向に進む。

| 状態 | 入る契機 | していること | パネルの表示 |
|---|---|---|---|
| 待機 | 起動、挿入の完了 | 何もしない。マイクは閉じている | 非表示 |
| 録音 | ホットキーを押す | マイクを開き、部分結果と確定済みの区間を受けて溜める | いまの全文の末尾 |
| 確定 | ホットキーを離す | マイクを閉じ（入力の終了で認識器が確定に進む）、残りの確定を待って全区間を連結する | 「確定中」 |
| 後処理 | 確定結果の到着 | 辞書置換 → コマンド判定 → 整形（有効時） | 「整形中」（整形が有効なときだけ） |
| 挿入 | 後処理の完了 | AX または貼り付け。コマンドがあれば Return | 字幕を閉じる。成功なら何も出さず、知らせることがあるときだけトーストを出す |

確定、後処理、挿入の間にホットキーを押しても、新しい録音は始めない。
パネルに「処理中のため受け付けません」と出す。
録音中に届いた押下は黙って捨てる（キーを押し続けている間に押下が繰り返し届く可能性があり、届くかは §9 で確かめる）。
確定結果が空のときは何も挿入せず、「認識結果がありません」と出して待機に戻る。
キーを一瞬だけ押して離し、音声が 1 つも届かなかった場合も同じ扱いにする。
認識器は、音声を 1 つも受け取らずに確定へ進むと結果の待ちが終わらない（実測）。
核がこれをエラーとして返すので、処理中のまま戻らなくなることはない。
話している最中に認識が失敗した場合（認識モデルが未導入など）は、キーを離すのを待たずに理由を出して待機に戻る。

マイクは録音状態の間だけ開く。
常時開いておけば発話の冒頭を落とさずに済むが、メニューバーのマイク使用表示が点いたままになり、録音の開始と終了を本人が握るという前提が崩れる。
認識器（SpeechAnalyzer と SpeechTranscriber）は発話ごとに作る。
handoff §2.2 の遅延は認識器を開始した後に音声を投入して測った値で、認識器の生成と開始、マイクが開くまでの時間は含まない。
この時間で冒頭が欠けるかは §7 で測り、欠けるなら、次の発話の認識器を挿入の完了時に先に作っておく形に変える。

### 3.5 後処理

順序は handoff §3 のとおりである。

**末尾コマンド。**
コマンドは二つある。
「送信して」は挿入の後に Return を送り、「改行して」は挿入の後に Shift+Return を送る。
改行を改行文字の挿入でなく Shift+Return にするのは、チャットの入力欄では Return が送信になり、ターミナルでは貼り付けた改行文字でコマンドが実行されうるからである。
「改行して」は本人の要望で足した（2026-10-09）。文中の「改行」を改行に変える案は、その語を本文として書けなくなるので退けた。
コマンドの照合は、表記ではなく読みで行う。
実機で「改行して」が「開業して」と認識されたためで、読みはどちらも「かいぎょうして」になる。
本当に「開業して」で言い切った文は改行になるが、末尾に限るので稀である。

設定 `newlineAfterUtterance` を有効にすると、コマンドが無くても、挿入のたびに Shift+Return を送る。
押して離すまでの 1 回の発話が 1 行になる。
メニューの「発話の後に改行する」で切り替えられ、`config.json` に書き戻す。
本人が実機で、1 回の発話の途中に「改行して」を挟もうとしたことから出た案である（2026-10-09）。
文の途中のコマンドを認める案（句点の直後に限る）より規則が単純で、認識の誤りに左右されない。
「送信して」があるときは送信を優先し、改行は送らない。

以下、「送信して」で規則を書く。「改行して」も同じ規則に従う。

辞書置換後の文字列から末尾の句読点と空白を除き、末尾が「送信して」に一致したら、その語を本文から除いて挿入し、挿入の後に Return を送る。
文中の「送信して」は本文として扱う。
本文が「送信して」だけなら、何も挿入せず Return だけを送る。
「このファイルを送信して」で話し終えた場合も送信になる。
これは末尾一致という規則の帰結で、Aqua Voice と同じ挙動である。

**LLM 整形。**
既定は無効で、メニューの「LLM で整える（フィラーと句読点）」で切り替える。
同音の認識誤り（「改行」が「開業」になる類）を LLM に直させる案は、実機の発話で測って退けた。
8B と 27B に、読みを変えない書き換えだけを通す検証を付けて試したところ、実際に出た誤り 5 件は、プロンプトを 2 通り変えても 1 件も直らなかった（2026-10-09）。
認識器が確定結果に付ける別候補も調べたが、中身は句読点と助詞の有無の違いで、同音の正しい語は入っていなかった。
一貫して起きる誤りは、読み辞書にその語を足すのが効く（「改行」を足すと「開業」が置き換わる。本当の「開業」は犠牲になる）。

有効にすると、コマンドを除いた本文を `http://127.0.0.1:8124/v1` の Qwen3-8B に投げる。
サーバはアプリから起動しない（本人が `mlx_lm.server` を立てる）。
確定から 1 秒以内に検証済みの結果が得られなければ、生テキスト（辞書置換後）を挿入する。
遅れて届いた結果は履歴にだけ残す。
整形の検証方式は ADR-6 に書く。

以下、この文書で「パネルに出す」と書いている理由や警告は、トーストに出る（ADR-8）。

## 4. 権限

| 権限 | 使う場面 | 無いときの挙動 |
|---|---|---|
| マイク | 録音 | 録音を始めず、パネルに「マイクの許可がありません」と設定画面への案内を出す |
| アクセシビリティ | AX での挿入、⌘V と Return の送出 | 認識は行い、挿入はしない。パネルに理由を出し、結果はメニューの「直前の発話をコピー」で取れる |
| 音声認識 | SpeechTranscriber | §9 のとおり要否が未確認。Info.plist に用途の文言は入れておく |

キーのホットキーは Carbon の `RegisterEventHotKey` で取るので、権限は要らない。
マウスボタンをホットキーにした場合だけ、その受け取りにもアクセシビリティの許可を使う（ADR-4）。
パスワード欄など、セキュア入力が有効な間（`IsSecureEventInputEnabled()` で判定）は挿入しない。
判定は二度行う。
キーを押した時点で有効なら録音を始めず、「セキュア入力中のため録音しません」と出す。
話している間にパスワード欄へフォーカスが移った場合に備え、挿入の直前にも見て、有効なら「セキュア入力中のため挿入しません」と出す。
どちらの場合も履歴には残さない。

## 5. 挿入方式

挿入は二段構えで、どちらの経路で入ったかを履歴に残す。

1. **AX。**
   システム全体のフォーカス要素を取り、`kAXSelectedTextAttribute` に文字列を書く。
   選択範囲があれば置換になり、なければカーソル位置への挿入になる。
2. **貼り付け。**
   クリップボードの全項目を退避し、文字列を置き、⌘V を送り、貼り付けが済んだ後に退避した内容を戻す。
   置く文字列には、クリップボード履歴アプリが拾わないための印（`org.nspasteboard.TransientType`）を付ける。
   戻す前に変更回数を見て、本人がその間に別のものをコピーしていたら戻さない。

AX から貼り付けに落とす条件は、二重挿入を避ける側に倒す。

- AX の書き込みがエラーを返した → 貼り付けに落とす
- 成功を返し、選択範囲（位置と長さ）と入力欄の内容（`kAXValue`）の両方が読めて、どちらも書き込みの前後で変わっていない → 入っていないと判断して貼り付けに落とす
- 成功を返したが、選択範囲か内容のどちらかが読めない → 入ったものとして扱う。パネルに「挿入を確認できませんでした」と出す

二つ目で内容まで見るのは、選択範囲だけでは入ったかどうかを決められないからである。
挿入した文字列を選択状態にするアプリでは長さだけが変わり、位置は動かない。
三つ目を貼り付けに落とさないのは、実際には入っていた場合に同じ文が二度入るからである。
入っていなかった場合は、メニューの「直前の発話をコピー」で取り戻せる。
文が失われるより二度入るほうが、送信済みのチャットでは取り返しがつかない。

三つ目の場合、末尾コマンドがあっても Return は送らない。
入っていない欄に Return だけが届くと、その欄に元からあった下書きが送信されるからである。
パネルには「挿入を確認できなかったため送信していません」と出す。

AX が「成功を返すのに入らない」アプリがどれだけあるかは、手元の知識では決められない。
§7 のアプリ別の確認で実測し、常に貼り付けを使うアプリを設定（bundle id の一覧）に書けるようにする。
この一覧の初期値は空で、実測で必要になったものだけを足す。

貼り付けの後、退避を戻すまでの待ち時間と、Return を送るまでの待ち時間も実測で決める。
短すぎると、戻した後の内容が貼られたり、貼り付けの前に Return が届いたりする。

## 6. 履歴

`~/Library/Application Support/Dictate/history.jsonl` に、1 行 1 イベントで追記する。
書き換えと削除はしない。

| イベント | 書く時点 | 項目 |
|---|---|---|
| `utterance` | 挿入の完了時 | id、発話開始時刻、録音秒数、生テキスト、run（文字列、信頼度、時刻）、辞書置換後、置換箇所、コマンド、挿入した文字列、挿入経路（ax、paste、none）と理由、前面アプリの bundle id、各段の所要時間 |
| `format` | 整形結果の到着時 | 発話の id、整形結果、判定（採用、時間切れ、検証で棄却、接続不可）、所要時間 |

整形を別イベントにするのは、予算を超えて遅れて届いた結果を、挿入済みの発話に後から足すためである。
追記専用のまま整形のやり直しもできる。

所要時間は、キーを離す → 確定 → 後処理の完了 → 挿入の完了、の各区間を記録する。
§7 の遅延はここから読む。

履歴は設定で無効にできる。
履歴には入力した本文がそのまま残るので、無効にする手段は最初から用意する。

## 7. 評価計画

評価は二つある。
挿入がアプリごとに通るかの確認と、本人の肉声 20 文による精度と遅延の計測である。

### 7.1 アプリ別の挿入確認

次のアプリの入力欄に、同じ 1 文を入れる。
挿入経路、二重挿入の有無、クリップボードが元に戻ったかを表にする。

TextEdit、メモ、Slack、Chrome（textarea と Gmail の本文）、VS Code、ターミナル、Claude デスクトップ。

この結果で §5 の「常に貼り付けを使うアプリ」と待ち時間を決める。

あわせて次の二つを 1 回ずつ確かめる。

- D を先に離し、⌃⌥ を遅れて離す。貼り付けの ⌘V と送信の Return に、押されたままの修飾キーが混ざらないか。
- 発話と発話の間に入力機器を切り替える（AirPods の接続など）。次の発話が録れるか。

### 7.2 肉声 20 文

20 文は付録 A に候補を置いた。
違うところだけ直してもらえば確定する。
読み上げなので、参照文は台本そのものである。

手順は次のとおり。

1. `eval/sheet.html`（20 行、台本と入力欄が並ぶローカルのページ）を Chrome で開く。
2. 各行の入力欄にカーソルを置き、ホットキーを押して台本を読む。言い損ねたら欄を消してやり直す。
3. ページの「書き出し」で、欄の内容を JSON にする。
4. `eval/score.py` が JSON と履歴を突き合わせて集計する。

突き合わせは文字列で行う。
各行の欄の内容（末尾の改行を除く）と「挿入した文字列」が一致する発話のうち、最も新しいものをその行の発話とする。
やり直しで履歴に残った余分な発話は、どの行とも一致しないので使われない。
一致する発話が無い行は未採点として一覧に出し、集計から黙って落とさない。
コマンド判定の正誤は、その発話の「コマンド」の項目で見る。

実際に挿入された文字列を採点するので、認識から挿入までの全経路を通した値になる。
話すのは 1 巡でよい。
辞書の有無と整形の有無は、履歴の生テキストから再計算して比べる。
整形は有効にして話し、生テキスト経路の遅延は各段の所要時間から読む。

測るものと、事前に置く基準は次のとおり。

| 指標 | 出し方 | 基準 |
|---|---|---|
| CER（表記のまま、読み正規化後） | 既存の `cer.py` と同じ規則。文体別にも出す | 置かない。肉声の初回計測である |
| 辞書の効き | 辞書あり、なしの CER 差と、置換が誤って当たった件数 | 誤置換 0 件 |
| コマンド判定 | 末尾「送信して」3 文と文中 1 文の正誤 | 4 文とも正しい |
| 発話冒頭の欠け | 文頭 3 文字の削除件数 | 置かない。多ければマイクの開き方を見直す |
| 遅延（整形なし、各段の合成） | キーを離してから確定までと、挿入の所要時間の和。整形を有効にして話すので実測ではなく合成値である。中央値と最大を出す | 中央値 0.5 秒以内（`06` §3 の要件は確定から挿入まで 0.5 秒。確定待ちを含めた厳しい側で置く） |
| 整形 | 完了時間の分布、時間切れ率、検証での棄却率、採用された結果の目視 | 置かない。採否は結果を見て本人が決める |

音声は保存しない。
本人の声だけなので規則上は置けるが、採点に要るのは挿入結果と履歴で、音声を使う工程が無い。

### 7.3 UI の確認

浮遊パネルは、本人の目視を完了条件にする。
`ui-preview` スキルはブラウザで動く画面とモックしたバックエンドを前提にしており、ネイティブのパネルには当てはまらない。
代わりに、アプリに `--demo` 起動を用意する。
マイクも認識も使わず、台本どおりの状態（部分結果が流れる、確定、整形で時間切れ、挿入の失敗、権限なし）をメニューから選んで再生する。

## 8. 判断の記録（ADR）

### ADR-1 共通核を最初から独立パッケージにする

- **状況**：元文書（`06` §3）は、議事録側がライブ字幕を必要とした時点で切り出す、としていた。handoff §1 と今回の依頼は、最初から独立パッケージにすると決めている。
- **決定**：`Packages/SpeechCore` に独自の `Package.swift` を置く。アプリは同じリポジトリからパス依存で取る。
- **理由**：パッケージが分かれていれば、核がアプリ側の型を参照した時点でビルドが通らない。境界を規約ではなくコンパイラが守る。
- **退けた案**：ルートの 1 パッケージに `SpeechCore` をライブラリとして並べる案。議事録側からも取り込めるが、核からアプリ側の対象を参照する誤りを `Package.swift` の依存宣言でしか防げない。
- **代償**：核の API を変えるとき、議事録側が取り込んだ後は相手の都合を見る必要がある。取り込みまでは自由に変える。

### ADR-2 Xcode なしで SwiftPM とスクリプトで組む

- **状況**：この機体に Xcode が無い。マイクとアクセシビリティの許可は、ターミナルではなくアプリに付けたい。
- **決定**：`swift build` の成果物を `scripts/bundle.sh` が `build/Dictate.app` に組む（Info.plist、`LSUIElement`、用途の文言、署名）。起動は `open build/Dictate.app`。
- **理由**：ターミナルから実行ファイルを直接起動すると、許可はターミナルに付く。挿入の権限がターミナルの権限と混ざり、他の機体や配布で再現しない。
- **退けた案**：Xcode を入れる案。大きなダウンロードで、承認が要る。試作に必要な機能は CLT で足りる。

### ADR-3 署名はアドホックで始め、妨げになったら自己署名の証明書に切り替える

- **現在の状態（2026-10-09）**：切り替え済み。ログインキーチェーンに自己署名のコード署名証明書「Dictate Dev」を本人の承認のうえで作り、`scripts/bundle.sh` はこの証明書があればそれで署名する。アプリの識別条件が「バンドル ID と証明書」になり、組み直しても同じアプリとして扱われる。
- **切り替えた理由**：実機確認に入ってから 1 日で 13 回組み直し、そのたびにアクセシビリティの許可を消して付け直すことになった。一覧では古い許可がオンのまま表示され、効いていないことが見た目で分からなかった。
- **証明書の削除**：`security delete-identity -c "Dictate Dev"`、またはキーチェーンアクセスで「Dictate Dev」の証明書と秘密鍵を消す。消すと `bundle.sh` はアドホック署名に戻る。
- **以下は承認時の判断**。

- **状況**：署名 ID が無い。アドホック署名のアプリは、ビルドのたびに OS から別のアプリとして扱われ、アクセシビリティとマイクの許可を付け直すことになる。
- **決定**：アドホック署名で始める。許可が要らない部分（`DictateKit` の後処理、SpeechCore の辞書）はテストで回し、アプリの組み直しを減らす。`--demo` も許可なしで動く。
- **切り替える条件**：許可の付け直しが実装と評価の妨げになったら、自己署名のコード署名証明書をログインキーチェーンに 1 枚作り、それで署名する。作成は本人の承認を得てから行い、作った事実と削除方法を報告に書く。
- **退けた案**：最初から自己署名証明書を作る案。許可は保たれるが、キーチェーンへの書き込みを試作の前提にすることになる。付け直しの回数は実装してみないと分からないので、先に小さいほうで始める。

### ADR-4 ホットキーは登録の窓で決め、キーは Carbon、マウスボタンはイベントタップで受ける

- **決定**：メニューの「ホットキーを登録…」で窓を出し、窓の上で押したキーの組み合わせかマウスボタンを捕まえて `config.json` に保存する。既定は ⌃⌥⌘D。
  - **キーと修飾キーの組み合わせ、ファンクションキーの単独**：`RegisterEventHotKey` で押下と解放を受ける。権限が要らず、登録した組み合わせしか届かない。
  - **マウスの中ボタンとサイドボタン（修飾キーつきも可）**：イベントタップで受ける。受け取る種類はマウスボタンの押下と解放だけで、キー入力は通らない。登録したボタンは前面アプリに渡さない（渡すと、サイドボタンでブラウザが前のページへ戻る）。アクセシビリティの許可が要る。
- **登録できないもの**：左クリックと右クリック、修飾キーだけの単独押し、⌃ ⌥ ⌘ のどれも付かない文字のキー。理由は窓に出す。同じ規則を `config.json` の読み込みにも使う。
- **修飾キーの単独押しを入れない理由**：右 ⌥ などを登録すると、そのキーを普通の修飾キーとして使うたびに録音が始まる。キーの押下を受け取らない限り「他のキーと一緒に押されたから取り消す」ができず、受け取ればキーロガーと同じ位置に立つ。本人の判断で範囲から外した（2026-10-09）。
- **競合の警告**：macOS 自体の有効なショートカットと同じ組み合わせは、`CopySymbolicHotKeys` で調べて窓に警告を出す（⌃Space、⌘Space などが当たることを実測）。他のアプリのホットキーは調べられない。`RegisterEventHotKey` は、他のアプリが同じ組み合わせを登録していても成功する。排他オプション（`kEventHotKeyExclusive`）を付けても同じだった（Rectangle が使う ⌃⌥D、⌃⌥F、⌃⌥← で実測）。窓には検出できない旨と、保存後に押して確かめる案内を出す。
- **経緯**：初版の既定は ⌃⌥Space で、OS の入力ソース切り替えと衝突した。次の ⌃⌥D は、本人の環境で Rectangle（ウインドウの幅を変えるアプリ）と衝突した。キーを設定ファイルに手で書く形では衝突のたびに書き直しになるので、登録の窓を足した。
- **短い押下**：0.3 秒未満で離した押下は、誤操作として何も出さずに捨てる。

### ADR-5 挿入は AX を先に試し、貼り付けに落とす

- **決定**：§5 のとおり。
- **理由**：AX はクリップボードに触れず、挿入が同期で終わる。貼り付けはほぼ全てのアプリで通るが、クリップボードを一時的に書き換え、待ち時間が要る。
- **退けた案**：常に貼り付ける案。実装は半分になるが、クリップボード履歴アプリへの混入と、復元の競合を全アプリで負う。キー入力を 1 文字ずつ送る案は、IME が有効だと変換に巻き込まれる。

### ADR-6 LLM 整形は出力を差分で検証し、通らなければ捨てる

- **状況**：8B は内容を落とし、発話にない単位を補う（handoff §2.3）。禁止文を強めても効かない。
- **決定**：二つの構造で守る。
  1. 数値の区間（数字と、数字に挟まれた記号）を番号つきの印に置き換えて渡し、戻りで元の文字列に戻す。印が欠けたり、増えたり、順序が変わったりした出力は捨てる。
  2. 入力と出力の差分を取り、差分が次の二種類だけであることを確かめる。それ以外の差分がある出力は捨てる。
     - 句読点と空白の追加、削除、置換。句読点は「、。，．！？」と改行に限る。数値の表記に使う「/」「:」「-」「,」「.」は含めない。
     - フィラーの語彙の削除。「えっと」「えーっと」「えーと」「ええと」「えー」「あのー」はどこでも削除できる。「あの」「その」「まあ」「なんか」は、生テキストで直後に読点があるときだけ削除できる。
- **理由**：検証を通った出力では、追加は句読点と空白に限られ、削除は句読点と空白とフィラーの語彙に限られる。単位の補完のような追加は、モデルの行儀に頼らず止まる。削除は語彙の範囲に縛られるが、語彙にある語が本文として使われ、かつ直後に読点がある場合（「その、件ですが」）は削られうる。
- **句読点の変更に付ける二つの制限**：隣り合う数値の間が記号と空白だけのとき（「3、4人」「3 4人」）、出力でもその並びが同じであることを求める。句読点と空白の変更を許すだけだと、「34人」にする出力が通る（実装のレビューで実測）。また、フィラーだけの発話を空にした出力は採用しない。挿入するものが無くなるからである。
- **空白と読点の削除を許す理由**：Apple は確定結果に自分で読点を打ち、数字の前に半角の空白を入れる（「えっと、」「栄養は 14時」）。フィラーと一緒に直後の読点を消す出力や、空白を詰める出力を棄却すると、整形がほぼ通らなくなる。
- **退けた案**：フィラーの除去をコードだけで行う案。「あの」「その」「まあ」は連体詞や副詞としても現れ、語彙の一致だけでは本文を削る。どの出現がフィラーかの判断を LLM に任せ、削ってよい語の範囲をコードが縛る。
- **代償**：検証が厳しく、棄却率が高ければ整形はほぼ効かない。§7.2 で棄却率を測り、採否を決める。数値マスクと差分検証は守る対象が重なる（単位の補完はどちらでも止まる）。マスクにしか止められないものもある。数字の内部への句読点の挿入（「3113」を「3,113」にする類）は、差分検証では句読点の追加として通りうる。マスクは handoff の確定判断でもあり、残す。「120の78」を「120/78」にする書き換えは、「の」がマスクの外にあるのでマスクでは止まらず、差分検証が止める。同じ位置で複数のフィラーが当たるときは、最も長いものの削除だけを認める。短い方も認めると、「えーと」の「えー」だけを削って「と」を残す出力が通る。語の途中から始まるフィラーは残っており、「へえー」を「へ」にする出力は検証を通る。直前が仮名なら認めない規則を試すと、「それでえーと明日」のような句読点のない連続を誤って棄却した。語彙は Apple が実際にフィラーをどう書くかを §7.2 で見てから決め直す。差分の照合は再帰で書いてあり、約 2,500 文字を超える入力でスタックが尽きる（実測）。30 秒の発話は 200 文字程度で、整形の出力長も 512 トークンで縛っているので届かないが、上限を上げるときは書き直しが要る。「あの」「その」に読点の条件を付けたので、Apple が読点を打たなかったフィラーは残る。どれだけ残るかも §7.2 で見る。

### ADR-7 履歴は追記専用の JSONL、音声は残さない

- **決定**：§6 のとおり。
- **理由**：辞書、コマンド判定、整形はどれも生テキストからの計算なので、生テキストと run が残っていれば全てやり直せる。音声が要るのは認識をやり直すときだけで、認識器は Apple 単独で固定している。
- **退けた案**：SQLite。検索も集計も今は要らず、`score.py` が行を読めれば足りる。

### ADR-8 表示は字幕とトーストの二つの窓に分け、成功は知らせない

- **決定**：`NSPanel`（`.nonactivatingPanel`、キーウィンドウにならない）を二つ、画面下端の中央に出す。メニューバーに状態表示とメニューを置く。
  - **字幕**：話している間の部分結果と、「確定中」「整形中」。幅は固定で、末尾を 1 行で見せる。挿入が済むと閉じる。
  - **トースト**：挿入できなかった理由、挿入を確認できなかったこと、整形を採用しなかったこと、受け付けなかった操作の理由。幅は文言に合わせ（文言部分で最大 660pt）、句点ごとに改行して全文を出す。文言は、1 文目に起きたこと、2 文目以降に次にすることを書く。1.7 秒に文言 1 文字あたり 0.06 秒を足した時間で閉じる。
- **フォーカスを取らない理由**：窓がフォーカスを取ると、前面アプリの入力欄からカーソルが外れ、挿入先が無くなる。
- **二つに分ける理由**：字幕と結果は、幅も、見せたい側（末尾か先頭か）も、出ている時間も違う。初版は 1 枚の窓で兼ねており、理由を読み切る前に次の発話を始めると字幕が上書きした。分けた後は、字幕が出ている間のトーストを字幕の上に逃がす。
- **成功を知らせない理由**：入力欄に文が入ること自体が成功の合図になる。AX と貼り付けのどちらで入ったかは画面では分からなくなるが、履歴には残る。
- **経緯**：二つとも本人の目視で決めた（2026-10-09）。表示時間は初版の 1.2 秒が早く感じられたため 0.5 秒延ばした。トーストの最大幅は初版の 440pt から 1.5 倍にした。
- **メニューの項目**：現在の設定の表示（整形の有効と無効と接続状態、履歴の有効と無効）、設定と辞書を再読み込み、直前の発話をコピー、終了。設定の切り替えはメニューに置かない。設定の正本を `config.json` の 1 か所にするためである（ADR-9）。

### ADR-9 設定は JSON ファイル 1 枚にする

- **決定**：`~/Library/Application Support/Dictate/config.json` に、ホットキー、整形の有効と宛先とモデル名と予算、履歴の有効、常に貼り付けるアプリの一覧を置く。無ければ既定値で起動する。壊れていれば、起動時にパネルで箇所を示して既定値では動かさない。項目名の打ち間違い（知らない項目）、修飾キーなしの英数字のホットキー、範囲外の予算も同じ扱いにする。
- **メニューから切り替える項目**：「発話の後に改行する」と「LLM で整える（フィラーと句読点）」は、書く先やサーバの起動状況によって頻繁に切り替えるので、メニューに置く。切り替えは `config.json` に書き戻す。
- **細かい項目の直し方**：メニューの「設定ファイルを開く」が、全項目を現在の値で書き出してから `config.json` を開く。項目名を覚えていなくても、違うところだけ直せばよい。メニューや登録の窓から書き換えたときも、全項目を書き出す。
- **整形の設定**：接続先、モデル、予算に加えて、`temperature`、`maxTokens`、`enableThinking`、`systemPrompt` を持つ。`systemPrompt` は `null` なら組み込みのプロンプトを使う。プロンプトを変えても、挿入されるのは ADR-6 の検証を通った出力だけである。
- **ホットキーの例外**：ホットキーだけは登録の窓から書く（ADR-4）。窓は `config.json` の `hotkey` を書き換える手段で、別の保存先は持たない。他の項目は書かれているまま残し、ファイルが壊れているときは上書きしない。
- **理由**：項目が少なく、変える頻度も低い。壊れた設定を黙って既定値に読み替えると、意図した設定が効いていないことに気付けない。
